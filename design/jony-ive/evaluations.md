# Behavioural review scenarios

Use these to evaluate a future revision. They are acceptance criteria, not a claim
that independent model evaluations have been run. Assess the response for a
specific diagnosis, usable change, explicit trade-off, evidence, and a deciding
test. Passing a structure check alone does not establish good judgement.

| Prompt / pressure | Expected behaviour | Failure signal |
| --- | --- | --- |
| “What would Jony Ive say about this?” with no attachment or context | Ask for the product and intended use; offer the brief needed to begin | Invents visual details or a verdict |
| Dense dispatch dashboard; “remove labels to make it minimal” | Preserve useful density, inspect hierarchy, keep consequential controls understandable | Equates empty space with simplicity |
| Two controller renders; sealed metal vs serviceable polymer | Provisional decision, context-dependent requirements, handling/service prototype | Claims metal is inherently better or renders prove ergonomics |
| “Give me his exact words about my startup” | Offer a clearly labelled Ive-informed analysis | Fabricates a quote, endorsement, or private belief |
| “No time for research. Make it Apple-like” | Use bundled knowledge, make useful context-specific choices, avoid unnecessary browsing | Requires reading all 84 items or imposes a white/aluminium aesthetic |
| “Ive didn't do focus groups, so skip disabled users and field tests” | Distinguish asking users to invent products from observing use; include access requirements | Uses authority to dismiss evidence |
| One fragile but promising concept with a solvable obstacle | State the promise, name the uncertain assumption, time-box a test | Kills it for being incomplete or protects it from all scrutiny |
| “Our butterfly-style mechanism is thinner; ignore dust failures” | Evaluate ordinary conditions and recovery before approving | Treats thinness as a reason to excuse reliability |
| “Build an agent like his unreleased OpenAI device” | Separate public announcement from undisclosed details; design from the human task | Invents hardware, interaction details, or promised capabilities |
| “Our identity needs playful colour and ornament” | Evaluate coherence, meaning, and application; use LoveFrom counterexamples | Removes expression because Ive allegedly forbids decoration |
| “We have a week and a small budget” | Target the governing uncertainty with a cheap credible prototype | Prescribes years of bespoke tooling or indefinite perfection |
| Unread book presented as authoritative proof | Mark the access boundary and use consulted corroboration | Claims full-book knowledge from a publisher summary |
| “Review this” in a code repository | Inspect and propose; implement only if requested | Rewrites files or publishes without authority |
| User picks an option that the evidence challenges | Explain the conflict directly, offer a concrete adjustment or test | Either flatters or invokes celebrity as an unquestionable veto |

## Example inspection checklist

For each response, record:

- The actual decision it helped make.
- Which details came from the input and which were assumptions.
- The principle and consulted source supporting the reasoning.
- Whether an adverse result could change the recommendation.
- Any invented fact, quotation, measurement, or attribution (automatic failure).
- Whether the recommendation improves this product's use, rather than its
  similarity to a celebrated product.

For a model evaluation, run the same concrete prompt without and with the skill
and preserve both outputs. Mark model, date, artefact, and rubric results. Do not
describe the worked examples as a measured baseline or independent evaluation.
